## Что было сломано и почему

Дайджесты не приходили подписчикам. Причина оказалась не в Telegram и не в
доставке, а в самом начале цепочки.

В JSON-схеме запроса к OpenAI стояло `format: "uri"`. Strict-режим Structured
Outputs это ключевое слово не поддерживает и отклоняет запрос целиком. Каждый
часовой запуск сбора падал, кандидаты не появлялись, редактору было нечего
утверждать, база материалов оставалась пустой — и любой выпуск получался
пустым. Бот отвечал «выпуск появится позже», что выглядело как проблема
доставки.

Диагностический признак: `/api/ready` показывал `latestIngestionAt: null` и
`latestApprovedSourceAt: null` при всех остальных проверках `ok`.

Попутно нашлись ещё три дефекта, каждый из которых сам по себе давал пустой
выпуск:

- первый выпуск после `/start` собирался в окне свежести частоты — для
  ежедневной подписки это 48 часов, то есть новичок получал выпуск, только
  если редакция утвердила материалы за последние два дня;
- пустой выпуск кэшировался под своим ключом навсегда: повторный `/start`
  возвращал ту же пустоту даже после появления материалов;
- запрос к OpenAI имел таймаут 90 секунд при лимите функции Vercel в 60 —
  платформа убивала его вместо осмысленной ошибки.

Всё перечисленное исправлено и выкачено 19 августа.

## Что мешает прямо сейчас

**Баланс OpenAI на нуле.** API отвечает `429 insufficient_quota`. Ключ рабочий,
модель `gpt-5.6-sol` аккаунту доступна — нужно пополнить платформенный баланс
(минимум 5 $, platform.openai.com → Settings → Billing). До пополнения сбор
новостей падает, теперь уже по этой причине.

**Материалы не утверждены.** Даже после пополнения выпуски не поедут
автоматически: AI кладёт кандидатов в очередь, но в дайджест попадает только
то, что редактор провёл через «Передать редактору» → «Утвердить». Это
продуктовое правило, а не недоработка.

## Что делается дальше

Переезд с Vercel на VPS (reg.ru). Причины — ограничения serverless, которые
кодом не лечатся:

- лимит выполнения функции 60 секунд на тарифе Hobby, поднять нельзя;
- фоновый цикл long polling умирает сразу после ответа;
- при таймауте функции апдейт Telegram уже помечен обработанным, повтор
  Telegram отбрасывается как дубль, подписчик молча остаётся без выпуска.

Сервер российский, поэтому схема такая: приложение на reg.ru, исходящие
запросы к Telegram и OpenAI через зарубежный прокси, приём сообщений — long
polling вместо вебхука (входящие вебхуки до российского адреса не доходят).

Код к этому готов: Node запускается с `--use-env-proxy`, вебхук снимается
запросом `DELETE /api/telegram/configuration`, цикл polling переживает любой
порядок операций. Пошагово — в [SERVER-MIGRATION.md](SERVER-MIGRATION.md),
конфигурация — в каталоге `deploy/`.

## Что стоит сделать помимо переезда

- **Снизить частоту сбора.** Сейчас ежечасно, 720 запусков в месяц с
  веб-поиском по 42 доменам. Для текущего числа подписчиков достаточно 4–6 раз
  в сутки — расход на OpenAI упадёт кратно.
- **Мониторинг свежести.** `/api/ready` возвращает `503`, когда сбор встал или
  утверждения прекратились. Стоит повесить внешнюю проверку: сегодняшняя
  поломка месяц оставалась незамеченной именно потому, что снаружи всё
  выглядело работающим.
- **Ротация секретов.** Токен бота, ключ OpenAI и пароль базы фигурировали в
  переписке при разборе — их разумно перевыпустить.

## Локальный запуск

Нужен Node 24. Без `DATABASE_URL` приложение работает на демо-данных в памяти —
поэтому локально всё выглядело исправным, пока прод стоял.

```bash
npm ci
cp .env.example .env.local     # заполнить
npm run dev
```

Перед любой выкаткой:

```bash
npm test && npm run lint && npm run build
```

Сборка ловит ошибки типов, которых не видно ни в тестах, ни в линтере.
